# DHR-002 — Desktop & Mobile Graphical QA Matrix

**Issue:** [#68](https://github.com/Diabolicdonut/Dinosaur-Horror-RPG/issues/68) · **Owner:** Integration Director (graphical acceptance) · **Status:** test design prepared; **browser runs NOT PERFORMED** · **Manifest:** [qa/dhr-002-matrix.json](../../qa/dhr-002-matrix.json) · **Evidence form:** [DHR-002-EVIDENCE-TEMPLATE.md](DHR-002-EVIDENCE-TEMPLATE.md).

## What this framework proves — and does not

1. **Automated / source validation:** `npm test` and `node --check tests/dhr-002-graphical-qa.test.mjs` protect the matrix's enumerated scope, HTML entrypoint contracts, deterministic three-scenario/three-mode save and action behavior, and accepted historical-revision fixtures. These are *not browser tests*.
2. **Actual browser verification:** A human or browser automation must open the exact built site, perform the steps below, observe rendering/interaction, and attach screenshots, short screen recordings (when useful), console observations and a completed evidence record. A green Actions run or Pages deployment is **not** graphical acceptance.
3. **Unintegrated work:** The cinematographic Hub HTML and tactical SVG viewer are reference *prototypes*. The DHR-077 portrait/vitals component and some audio selectors exist as isolated modules; they are not evidence of Party layout integration or live playback. PR #135 (Hub) and PR #137 (live Dropbox/Worker media) were on separate integration holds when this matrix was prepared. Mark missing features **BLOCKED—NOT INTEGRATED**, not PASS and not FAIL for a feature the accepted product never promised yet. Once their implementation is merged, promote the applicable rows to mandatory browser checks.

No test in this document is pre-marked passed. No private Free League material, token, unpublished game secrets, or real save is checked in with this matrix.

On desktop use Chrome/Chromium with mouse/keyboard; for tablet/mobile use real touch hardware at least once and record when only an emulator was available. This is **3 adventures × 3 modes × 4 viewports = 36 distinct cases**, not 36 successful results. The structured target list is in the JSON manifest.

### Universal smoke sequence — repeat at each cell

1. **G01 Launch/identity:** Open `characters.html`, create or restore a legal roster and launch `party.html`. Choose one of the three actual playable adventure entries and confirm reset only after saving the preceding incident. Observe correct title, source-local starting room, exits, objective text, actors and seed. Browser console must have no uncaught startup error. Refresh once and verify restored scenario, not accidental new adventure.
2. **G02 Roster:** Click survivor tiles, view sheets/status, switch camera to a different survivor and return. Inspect names, roles, equipment and per-actor information. Repeat the 1- and 8-character edge cases at representative desktop and narrow mobile dimensions; note any wrapping, vertical scrolling or mistaken hidden buttons. Roster generation/edit is tested separately in the Character Lab.
3. **G03 Control ownership:** In Party, issue one legal `wait` for the correct scheduled survivor. Switch to **Character/Focus** and select another survivor; verify pause and owner labels, issue one player action when that actor actually owns the turn; one-step companion turns as necessary. Switch to **Spectator**, verify pause, single-step, resume and pause again. Return to Party. Record pre-/post- action index, beat, inventory and mode from permitted exports: **mode and camera switches alone must not roll dice, move animals or consume gear**. Switching camera never implies taking control.
4. **G04 Narrative/dice:** Submit a local observation and an authored skill/objective interaction; check that visible success/failure, stress, push (if authorized), transcript and objective changes agree with the resulting state. Attempt a nonsensical command or out-of-range action; no phantom state change, unearned evidence or hidden dice leak should follow. In ordinary play dice can remain hidden; any diagnostic dice view must be an explicit opt-in.
5. **G05 Inventory:** Acquire a **physically present** permitted item and compare inventory before/after, including other observers; verify an unavailable/remote item cannot appear by command. Test gear consumption/equipment restriction only with a source-valid scenario and active implemented mechanic. Do not assume every adventure has the same keycard.
6. **G06 Animal/NPC:** Seek an optional quiet or wonder observation, then a legitimate dinosaur encounter at a seed/location where present, without forcing a fight in every adventure. Check local proximity, LOS, redaction, survivor-specific journals and sound/portrait visibility. Talk to a colocated authored NPC where that scenario provides one; verify other-room or unearned NPC dialogue is not presented as witnessed fact.
7. **G07 Danger/combat:** In a separate disposable incident or known encounter seed, test accepted combat controls and available defense/reaction, attack or retreat options. Compare turn order, equipment, health, stress, condition, injuries and event history. Mark future standalone modules **BLOCKED—NOT INTEGRATED** where they are not wired to the runtime; do not mistake source-only resolver tests for a successful gameplay screen.
8. **G08 Save/recover:** Export/download the incident, record seed/revision/mode/beat (redacted). Use **Save**, reload the tab, **Load**, inspect actor positions, inventory, objectives and history; repeat with interrupted playback or offline mode. Confirm a rejected action doesn't corrupt the save. Re-starting another scenario must warn before replacing the current Party state. See historical exercises below.
9. **G09 Responsiveness & accessibility:** On the current viewport, test scrolling, safe area, browser zoom, long text, modal/dialog focus, contrast, visible focus, announcements and no horizontal clipping of critical controls. Repeat the command with keyboard-only navigation and with **actual touch** for the appropriate device. Test portrait/map options only if integrated.
10. **G10 Optional presentation:** When a real Hub, Map, portraits or scene still is integrated, perform its separate checklist below; otherwise mark as `BLOCKED` with source PR/issue. An attractive standalone demo is not a passed production feature.
11. **G11 Media/network:** In offline or permission-denied mode, verify local playable operations still work and no audio/video/picture request mutates game state. With approved credentials, test media mute/volume/gesture/failure on two real browser engines and record separate deployed-worker evidence.

## Separate acceptance exercises

**Legacy Nublar solo — `index.html`:** It does **not** have Party/Focus/Spectator; test `NEW INCIDENT`, local command form, map, inventory, hidden-dice effects, `SAVE`, `LOAD`, `EXPORT SAVE`, `EXPORT DEBUG`, AI disabled/error fallback and token redaction. Refresh must restore compatible autosave without resetting or clearing unrelated storage. Record a separate `LEGACY-INDEX-<viewport>` run; never enter three-mode PASS for this route.

**Character Lab — `characters.html`:** For sizes 1, 3, 4 and 8: enter deterministic seed, generate/regenerate, select survivor, lock/reroll a field, edit legal career and attribute/skill budget, manage two distinct equipment choices, validate, export roster, start Party. An invalid career/gear/budget must be detected without sneaking into the gameplay state. Verify keyboard accessibility of dynamic buttons and labelled editor fields.

**Historical saves / versioned worlds:** Use the seven public deterministic *construction fixtures* from `tests/fixtures/dhr-006-seed-incident-fixtures.mjs`: Nublar bound/unbound v3, Long Count current rev13 plus frozen rev1/rev12, Tidal current rev2 plus frozen rev1. `tests/seed-save-replay-dhr006.test.mjs` validates engine-level construction and replay; **browser acceptance additionally** requires obtaining an authorized, compatible exported test save (or constructing one with the real engine in a local test harness), importing/restoring only through an **actually available** UI path, and recording whether the loader supports it. Today's Party UI has Save/Load/Export but does **not** expose a general JSON import screen: mark “import through UI” **BLOCKED—NOT IMPLEMENTED**, not a fake PASS; use safe localStorage fixture setup in a disposable browser profile only when authorized. Verify old source revision remains unchanged after one legal action, that mode/roster/seed/replay remain valid, and that corrupt/mismatched/foreign keys are rejected without clobbering an unrelated good save. Never set a fake “passed” result merely because the unit fixture succeeds.

**Keyboard and assistive-tech:** Starting at the document top, Tab/Shift+Tab through every clickable control, Enter/Space activates appropriate buttons, arrow keys navigate native selects, Escape closes overlays if implemented, focus remains visible after dynamic rerender and never becomes trapped/lost. Screen-reader pass (NVDA/Firefox or VoiceOver/Safari) checks accessible names, heading structure, state/status announcements, error relationships, form labels, and whether non-color cues describe health/stress and dangerous actions. Zoom **200%** on desktop and **400%** at 320 CSS px effective width; test reduced-motion preference and high-contrast/forced-colors where supported. Report, don't conceal, inaccessible elements.

**Touch & orientation:** On real iOS Safari and Android Chrome, tap/select each control with one finger, type in command form using onscreen keyboard, dismiss keyboard, rotate portrait ↔ landscape, pan/scroll without accidental actions, resume from background tab/app and test a long narrative log. Record lost focus, viewport shift, clipped footer, accidental hover-only controls, touch target size and back-button behavior.

**Adventure Hub (UI-01/02/03, pending integration):** Verify Home/Continue, Adventures, Campaigns, Saves, Character Manager and Settings; real authored choices launch with selected party/mode and explicit warning; preview-only fictional scenarios cannot launch; chosen manifest/seed survives briefing. Hub demo localStorage is never treated as game save. Test multiple slots, import compatibility, overwrite/cancel and rejection of malformed saves *only when the actual production archive is merged*.

**Tactical Map (UI-04, reference-only until integrated):** Map in right-hand column is an observer-limited read-only projection, **not** a place to move a token via WASD/arrows or tap-to-teleport. Verify known rooms, LOS/fog, lighting, discovered threats, panning, zoom, centering by double-click/tap alternative, keyboard-accessible controls and map ↔ still toggles. Compare game save before/after view-only interactions: no action count, RNG, map physics or objective changes.

**Portraits/Health/Stress (UI-05, isolated component until mounted):** 1–8 survivors, selected/focused camera independent of who owns the turn, accessible status text, stress-driven stylized waveform, real health-based color and **flatline only on engine-confirmed death**, not merely zero HP/incapacitation. Check reduced motion, hide/show portrait row and character sheet popover with view-limited data. If the UI is not mounted, record integration blocker rather than rendering a source-only module in a prototype and calling it accepted.

**Audio/image/video (MEDIA-01/02):** Test normal low-volume ambience, silence, fade/crossfade, overlapping SFX, mute/volume persistence, mobile autoplay user-gesture restrictions, unavailable Dropbox files, HTTP 206/range **only for an actually deployed authenticated stream**, clip skip, return from image/video to map and local fallback without invented predator knowledge. Sound selection tests do not prove audible playback; mock video links do not prove production cutscenes.

## Recording results and reporting defects

Use a copy of [the evidence template](DHR-002-EVIDENCE-TEMPLATE.md) per browser/build with one row per actual case. Recommended artifact names: `DHR002_<sha7>_<case>_<browser>_<viewport>_<UTC>_before.png`, `..._after.png`, plus scrubbed console, seed and replay trace. Keep raw save/debug state, personally identifying data and tokens in restricted storage; attach only scrubbed information to public issues.

**Status is per cell and per test:** `PASS` = observed steps and expected result in a real browser with evidence; `FAIL` = reproducible mismatch (issue link required); `BLOCKED` = unavailable build/hardware/feature/dependency (specific reason); `NOT_RUN` = no execution; `NOT_APPLICABLE` = legitimately outside a case with a rationale. Automated source checks should be listed in a **separate section** and must never silently populate graphical statuses.

For a defect, open **a new GitHub issue** scoped to the actual feature owner; include scenario, mode, build SHA, seed, browser/device, viewport, exact reproduction steps, expected versus actual result, sanitized evidence, severity, and regression linkage. Do **not** fix gameplay, Worker or shared Party UI as part of DHR-002. Deduplicate against existing issues/held PRs and link the failure row to the new or existing defect. If a possible secret leak is involved, use private/security coordination rather than publishing credentials or undiscovered GM state.

4. Triage each FAIL into a linked GitHub issue. Re-run affected cases on the **fix's exact merged-main build** and capture before/after evidence; do not erase prior failures.
